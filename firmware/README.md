# Прошивка SvitloBoard 2

SvitloBoard 2 не читає EEPROM-налаштування старої прошивки SvitloBoard 1. Внутрішня
схема конфігурації ранніх випусків SvitloBoard 2 мігрує автоматично.

## Поточна поведінка

- перший запуск і явне скидання до заводських налаштувань запускають точку доступу
  `SvitloBoard-XXXXXX`;
- пароль точки доступу — `svitlobot`;
- локальна вебпанель зберігає основну Wi-Fi мережу, вибір СвітлоБот/custom URL та
  необов'язковий пароль адміністратора;
- три Wi-Fi профілі перевіряються одразу, починаючи з останнього успішного; кожна
  спроба обмежена в часі, повтори мають експоненційну затримку, а за недоступності
  всіх профілів вмикається резервна точка доступу;
- недоступність API не спричиняє перемикання між Wi-Fi профілями;
- налаштування зберігаються у двох слотах LittleFS із CRC та номером покоління;
- чотири справжні ввімкнення живлення, кожне з яких перервано протягом перших восьми
  секунд, стирають завершене налаштування; програмні перезапуски, OTA та watchdog
  не збільшують цей лічильник;
- запити до СвітлоБота використовують перевірений HTTPS; custom URL викликається
  методом GET точно як введено й може використовувати HTTP або HTTPS;
- HTTPS перевіряє ім'я сервера, використовує час із NTP та вбудований кореневий
  сертифікат GTS Root R4; приватні й самопідписані CA зараз не підтримуються;
- звичайні сигнали надсилаються не частіше ніж раз на 30 секунд, типове значення —
  раз на 60 секунд;
- опційне рознесення запитів за NTP дає 2–4 платам окремі слоти з кроком 45 секунд;
- OTA відхиляє бінарники без маркера поточної цільової плати; це захищає від
  поширених випадкових помилок, але не є криптографічним підписом;
- однаковий адаптивний AJAX-інтерфейс використовується на всіх платах; недоступні
  можливості приховуються за даними capabilities, які повертає прошивка;
- розділ «Перевірка статусу» показує сторінку СвітлоБота або локальний результат
  custom-запиту в `iframe`; перегляд локального результату не викликає custom URL;
  кнопка «Оновити» має п'ятисекундне обмеження частоти.

## Розклад кількох пристроїв

Режим рознесення запитів вимкнений за замовчуванням, зокрема після міграції старої
конфігурації. На платах, які ділять спільний ліміт API, увімкніть його, вкажіть
однакову кількість пристроїв (2–4) та унікальний номер кожної плати (від 1).
Номери не узгоджуються між платами автоматично: однакові номери або різна кількість
пристроїв можуть спричинити збіг запитів.

| Кількість плат | Інтервал кожної плати | Зсуви від початку спільного циклу |
| --- | ---: | --- |
| 2 | 90 с | 0, 45 с |
| 3 | 135 с | 0, 45, 90 с |
| 4 | 180 с | 0, 45, 90, 135 с |

Цикл прив'язаний до часу NTP, а не до завершення попереднього запиту. Між
запланованими запитами сусідніх плат є 45 секунд, включно з переходом між циклами;
це дає 15 секунд запасу відносно мінімального проміжку API у 30 секунд, але не
гарантує відсутності `429` за великих мережевих затримок чи сторонніх запитів.
Після запуску або відновлення Wi-Fi плата чекає наступного власного слота.
Пропущені слоти не надолужуються; корекція годинника не повинна повторити вже
використаний слот. Без коректного часу запити чекають, навіть для custom HTTP URL.

Звичайний інтервал ping не перезаписується й застосовується після вимкнення режиму.
На платах з експертним входом поставлений у чергу `OFF` використовує той самий
дозволений слот замість звичайного ping; рознесення може відкласти повідомлення до
наступного слота. Коли режим вимкнений, поведінка експертного входу не змінюється.

СвітлоБот визначає офлайн конкретного каналу після чотирьох хвилин без запитів.
Усі плати з одним ключем підтримують цей канал онлайн; для незалежних точок живлення
потрібні окремі ключі. Навіть одна працююча плата з групи надсилає частіше ніж раз
на чотири хвилини, але за трьох або чотирьох плат один невдалий запит уже дає
270 або 360 секунд між успішними запитами цього пристрою. Для двох — 180 секунд.

## Єдиний інтерфейс і capabilities

Кожна плата отримує той самий `WebUi.h`: однаковий дизайн, картки знайдених Wi-Fi
мереж і ручний варіант для прихованого SSID. Прошивка повідомляє сторінці кількість
Wi-Fi профілів та доступність OTA, журналу, захисту й експертного входу; сторінка
приховує лише непідтримувані елементи.

| Цільові плати | Доступні можливості |
| --- | --- |
| ESP-01 512 КБ | три Wi-Fi профілі, статус, журнал, захист панелі й factory reset; без OTA та експертного GPIO |
| ESP-01/ESP-01S 1 МБ | три Wi-Fi профілі, статус, журнал, захист панелі й OTA; без експертного GPIO |
| Sonoff Basic R2/R3, D1 mini, NodeMCU v2, ESP32 | три Wi-Fi профілі, статус, журнал, захист панелі, OTA й експертний вхід |

Для єдиного UI збірка ESP-01 512 КБ використовує 24 КБ LittleFS замість 32 КБ;
цього достатньо для двох CRC-перевірених слотів конфігурації та двох слотів
лічильника аварійного відновлення. Скидання чотирма короткими циклами фізичного
живлення доступне на кожній платі. Збірки ESP-01/ESP-01S не мають експертного GPIO:
GPIO0/GPIO2 впливають на режим завантаження і не дозволені для цієї функції.

Перехід уже прошитого ESP-01 512 КБ зі старої 32-КБ розмітки LittleFS на 24-КБ
змінює адресу файлової системи. Після першого встановлення такого образу через UART
налаштування потрібно ввести заново; для інших таргетів розмітка не змінюється.

## Збірка

Встановіть PlatformIO Core і запустіть типову збірку всіх дев'яти цілей:

```sh
pio run -d firmware
```

Окремі середовища:

```sh
pio run -d firmware -e esp01_512k
pio run -d firmware -e esp01_1m
pio run -d firmware -e d1_mini
pio run -d firmware -e nodemcuv2
pio run -d firmware -e sonoff_basic_r2
pio run -d firmware -e sonoff_basic_r3
pio run -d firmware -e esp32dev
pio run -d firmware -e esp32-c3
pio run -d firmware -e esp32-s3
```

`esp01_512k` — профіль можливостей для встановлення через послідовний порт, без OTA
та експертного GPIO, але з тим самим вебінтерфейсом. TLS не вимикається заради
меншого бінарника.

`sonoff_basic_r2` і `sonoff_basic_r3` призначені для штатного ESP8285 з 1 МБ
flash-пам'яті. SvitloBoard примусово утримує вбудоване реле вимкненим і не надає
елементів керування ним: ці плати працюють лише як індикатори доступності.

CI позначає збірки з `main` як `2.2.0-dev.<SHA>`; їх пропонує браузерний інсталятор.
Це позначення походження збірки, а не режиму оптимізації чи типу плати. Тег
`v2.2.0` створює випуск `2.2.0` без суфікса `prod` у GitHub Releases. Локальна
збірка без `SVB_FIRMWARE_VERSION` використовує `2.2.0-dev`; коміт додається окремо
до метаданих панелі. Публікація релізу за тегом не замінює образи інсталятора з `main`.

## Безпека

Експертний вхід живлення — це **лише цифровий низьковольтний вхід**. Ніколи не
підключайте 230 В, резистивний дільник або неізольовану схему безпосередньо до ESP.
Використовуйте сертифікований ізольований модуль, забезпечте резервне живлення плати,
роутера й ONT, а роботи з мережевою напругою доручайте кваліфікованому електрику.
`channelPingOff` повідомляє про зникнення живлення, але нічого не перемикає і не
від'єднує. Він доступний лише для режиму СвітлоБота; окремий OFF-запит для custom URL
у поточній схемі не визначений.

Додатково дивіться [опис архітектури](../docs/architecture.md),
[вимоги до входу живлення](../docs/hardware-power-input.md) і
[план розвитку](../docs/roadmap.md). Процедура приймання випуску наведена у
[плані тестування](../docs/test-plan.md).

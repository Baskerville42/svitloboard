# Архітектура SvitloBoard 2

SvitloBoard 2 — нова прошивка з власним контрактом поведінки та чіткими межами
модулів. Поведінка версії 1 використана як продуктова вимога, але її вихідний код
не є залежністю і залишається лише в історії Git.

## Послідовність роботи

```text
запуск
  ├─ ConfigStore: монтує LittleFS, перевіряє обидва записи, обирає найновіше покоління
  ├─ BootRecovery: рахує лише швидкі фізичні цикли живлення; очищає лічильник через 8 с
  ├─ WifiManager: перевіряє останню успішну, основну, потім резервні мережі
  │    └─ усі недоступні → режим AP+STA з обмеженою експоненційною затримкою повторів
  ├─ WebApp: перше налаштування та локальний AJAX API
  ├─ SvitlobotClient: вибраний backend → за потреби NTP/TLS → звичайний таймер або слот СвітлоБота
  └─ PowerMonitor: необов'язковий ізольований цифровий вхід → фільтр дребезгу → подія OFF,
       зокрема коли під час запуску вхід уже показує відсутність живлення
```

Усі періодичні операції виконує `loop()` із таймерами, безпечними до переповнення.
Невдалий запит до СвітлоБота не спричиняє перемикання Wi-Fi мережі. Підключення до
Wi-Fi, доступність сервісу, TLS і код HTTP — окремі діагностичні стани.

## Надійність конфігурації

Кожен запис містить сигнатуру, версію схеми, розмір, номер покоління, поля фіксованої
довжини та CRC32. Запис завжди виконується у неактивний слот, після чого зчитується й
перевіряється. Лише після успішної перевірки він стає новою актуальною версією. Якщо
живлення зникне під час запису, попереднє коректне покоління залишиться доступним.
Схема 2 додає явний тип отримувача та custom URL. Коректний запис схеми 1 автоматично
переноситься в режим СвітлоБота й одразу зберігається у новому форматі. Сигнали
присутності й опитування статусу не записують flash; запис відбувається лише
після явної зміни налаштувань або зміни останнього успішного Wi-Fi профілю.
Схема 3 додає два байти: кількість плат (0 означає вимкнений режим) і номер плати.
Записи схем 1 і 2 переносяться зі збереженням налаштувань; режим рознесення лишається
вимкненим, а попередній інтервал ping зберігається. Після перезапису обох слотів
схемою 3 старі прошивки цих налаштувань уже не прочитають. Перед відкатом збережіть
значення для повторного налаштування.

Структура EEPROM версії 1 не читається. Перший запуск версії 2 відкриває налаштування,
не трактуючи стерті чи випадкові байти як C-структуру. Так усувається цикл заводського
скидання старої версії замість перенесення небезпечного формату в нову архітектуру.

Лічильник аварійного відновлення відокремлений від конфігурації й також використовує
два записи LittleFS із поколінням та CRC. Його збільшує лише підтверджене платформою
ввімкнення живлення. Чотири запуски, перервані раніше ніж через вісім секунд,
спричиняють заводське скидання; вісім секунд стабільної роботи очищають лічильник.
OTA, програмний перезапуск, виняток і watchdog навмисно ігноруються, щоб оновлення чи
цикл аварій не стерли облікові дані.

## Політика Wi-Fi

- основна та дві резервні мережі;
- перша спроба одразу під час запуску;
- не більше 12 секунд на одну спробу підключення;
- спочатку остання успішна мережа, далі кожен увімкнений профіль по одному разу;
- резервна точка доступу після повного невдалого циклу;
- експоненційна затримка повторів із межею п'ять хвилин;
- жодного перемикання лише через недоступність DNS, TLS або API;
- перевірка довжини кандидатних налаштувань до заміни збереженого запису.

## Отримувачі, HTTPS і частота API-запитів

Конфігурація явно зберігає один із двох backend-ів. У режимі СвітлоБота прошивка будує
штатний `channelPing` URL з окремо збереженого ключа. У custom-режимі вона виконує GET
за повною адресою точно як її ввів користувач, нічого не додаючи до path або query.
URL має починатися з `http://` чи `https://`; fragment і credentials у authority
відхиляються.

Для HTTPS клієнт перевіряє ім'я сервера та ланцюжок до Google Trust Services R4 і
чекає на NTP перед TLS-перевіркою. Відбиток кінцевого сертифіката не закріплюється,
довільний trust anchor не зберігається, а режиму `setInsecure()` немає. HTTP дозволено
тільки для явно введеного custom URL і він не забезпечує конфіденційність. Запит
обмежений 6,5 секунди. Типовий інтервал сигналів — 60 секунд, а примусово надіслати їх
частіше ніж раз на 30 секунд не можна. Повтор `OFF` для СвітлоБота починається з 30
секунд і збільшується до п'яти хвилин; custom OFF-контракт поки не визначено.

Лише для backend СвітлоБота опційний режим рознесення використовує спільний цикл
тривалістю `45 × N` секунд, де `N` — 2–4 плати, і зсув `45 × (номер − 1)` секунд.
Усі плати повинні мати однакове `N` та різні номери від 1 до `N`; їхній розклад
обчислюється за часом NTP.
Це дає інтервали 90/135/180 секунд на плату й 45 секунд між сусідніми слотами.
Звичайний інтервал зберігається окремо й використовується після вимкнення режиму.
У custom-режимі рознесення завжди неактивне, а збережені прапорець, кількість і номер
плати не скидаються під час перемикання backend. Custom HTTP працює без NTP;
custom HTTPS чекає часу лише для перевірки TLS. Обидва використовують звичайний
інтервал ping. Правило слотів належить API СвітлоБота, а не всім отримувачам статусу.

У режимі рознесення після запуску й відновлення Wi-Fi клієнт чекає наступного
власного слота.
Пропущені слоти не надолужуються, а відправлення не зсуває наступний цикл.
Облік використаного слота запобігає повторенню після корекції NTP. Запити й повтори
СвітлоБота, включно з поставленим у чергу `OFF`, проходять через той самий дозвіл
відправлення; `OFF` займає слот замість ping. Коли рознесення вимкнене, чинні правила експертного
входу й повторів зберігаються. Запас у 15 секунд відносно мінімуму API не захищає
від сторонніх запитів або довільних мережевих затримок.

Чотирихвилинний таймаут СвітлоБота стосується окремого каналу, тому незалежні точки
живлення потребують різних ключів. Працююча плата підтримує спільний ключ онлайн
навіть за відключення інших. Максимальний інтервал окремої плати — 180 секунд, але
один невдалий запит за трьох або чотирьох плат дає відповідно 270 або 360 секунд
між успішними запитами й може спричинити офлайн її каналу.

Кореневий сертифікат чинний до 2036 року, але поведінку ланцюжка перевіряють у CI та
під час підготовки випусків. Оновлення CA — обслуговування прошивки, а не параметр
експертного інтерфейсу.

## Безпека локальної вебпанелі

Портал першого налаштування не повертає збережені паролі. Після налаштування сторінку
й API може захищати необов'язковий пароль адміністратора через HTTP Basic. Запити, що
змінюють стан, додатково вимагають спеціальний заголовок, тому звичайна стороння
HTML-форма не може спричинити конфігурацію чи скидання.

Маршрут `/status-frame` також проходить локальну авторизацію. Для СвітлоБота він
переспрямовує `iframe` на сторінку статусу з URL-кодованим ключем. Для custom backend
повертає локальний результат останнього запиту й не звертається до URL додатково.
Кнопка в браузері перезавантажує тільки `iframe` і не дозволяє повторне натискання
протягом п'яти секунд.

Цього достатньо для довіреної локальної мережі, але це не рівнозначно локальному
HTTPS. Варто встановити пароль адміністратора й не користуватися ворожими спільними
мережами.

## Модель OTA

ESP32 використовує два розділи програми по 1,5 МБ. На ESP8266 OTA увімкнено лише для
розміток flash, де є місце для проміжного образу. ESP-01 512 КБ оновлюється тільки
через послідовний порт. Для ESP32 фабричний образ браузерного встановлення та образ
локального OTA — різні файли.

Для 1 МБ ESP8266 із розміткою `1m64` релізний OTA-образ не може перевищувати
479 232 байти — це гарантує оновлення з попереднього випуску. Отримані браузером
100% даних ще не означають успішного запису: завеликий образ відхиляється під час
фінального запису в OTA-слот. CI та перевірка артефактів застосовують ту саму межу.

Поточне OTA покладається на перевірку формату в Arduino Core і вимагає маркер цільової
плати SvitloBoard усередині бінарника. Це запобігає типовим випадковим помилкам,
наприклад завантаженню образу D1 mini на Sonoff, але маркер не є криптографічним
підписом або межею безпеки. Подальше посилення перевірки OTA описано у
[плані розвитку](roadmap.md).
